# Factory and Generated-Application Quality Dimensions

## Purpose

This document defines the two-layer quality model for `upi_dispute_resolution_factory`.

The project must evaluate quality at two levels:

1. **Factory quality dimensions**: the quality of the governed software factory itself.
2. **Generated application quality dimensions**: the quality of applications produced or regenerated by the factory.

This prevents a common failure mode in agentic software generation: validating the factory mechanics while forgetting the quality of the application being generated, or testing the application while ignoring the governance quality of the factory that produced it.

## Layer 1: Factory quality dimensions

The factory itself must be evaluated for:

- **Validation**: deterministic validators, pass/fail reports, and repeatable validation gates.
- **Evaluation**: quality assessment of prompts, agent outputs, workflow outputs, generated artifacts, and review readiness.
- **Observability**: structured audit events today, and future traces, metrics, logs, run IDs, agent IDs, workflow step IDs, and failure classifications.
- **Traceability**: requirement IDs, task IDs, policy IDs, evidence references, input references, output references, and producing agent or workflow step.
- **Provenance and auditability**: artifact origin, hash, generation context, baseline provenance, run context, and release evidence.
- **Security and AI safety**: prompt-injection awareness, mock-boundary preservation, no unapproved production claims, no secret leakage, no excessive agency, and no fake validation results.
- **Workflow resilience**: checkpoints, blocked states, pause/resume metadata, human-review gates, and deterministic failure handling.
- **Debuggability**: beginner-readable scripts, deterministic behavior, explicit errors, clear next safe command, and easy terminal inspection.
- **Operational readiness**: supportability, troubleshooting notes, runbooks, and failure diagnosis paths.
- **Human review and approval**: no merge, tag, release, or completion claim without evidence and appropriate review readiness.

## Layer 2: Generated application quality dimensions

Applications generated by the factory must be evaluated for:

- **Functional correctness**: requirement-backed behavior for positive, negative, boundary, and edge scenarios.
- **API and data contracts**: explicit models, schemas, route contracts, state transitions, and error shapes.
- **Input and business validation**: clear validation for inputs, state transitions, mock assumptions, and invalid operations.
- **Testability and regression coverage**: unit tests, API tests, contract tests, boundary tests, negative tests, and regression tests.
- **Application evaluation**: quality review for functional fit, clarity, maintainability, supportability, and domain-risk assumptions.
- **Application observability**: health/readiness checks today, and future structured logs, trace IDs, metrics, correlation IDs, and actionable failure signals.
- **Application security**: safe defaults, input validation, no secret leakage, safe error messages, and explicit mock boundaries.
- **Reliability and resilience**: safe error handling, idempotency expectations, retry caution, deterministic behavior, and clear failure modes.
- **Performance and resource awareness**: lightweight implementation, local CPU awareness, and documented performance assumptions.
- **Maintainability**: beginner-readable, debug-friendly, modular code with clear names and low unnecessary abstraction.
- **Application operational readiness**: startup instructions, validation commands, troubleshooting guide, and support notes.
- **Compliance and mock boundaries**: official facts must be distinguished from synthetic assumptions; honesty labels must remain visible.

## Prompting requirement

Every future agent prompt that generates, evaluates, validates, reviews, or releases work must explicitly consider both layers:

- factory quality dimensions
- generated application quality dimensions

A response is incomplete if it only says tests passed but ignores evaluation, observability, operational readiness, traceability, auditability, or generated-application quality.

## Practical review questions

Before accepting any generated artifact, ask:

1. What requirement, task, policy, and evidence does it link to?
2. What validation proves it works?
3. What evaluation proves it is good enough?
4. What observability will help diagnose failures?
5. What audit trail proves who or what produced it?
6. What security and safety risks exist?
7. What mock boundaries remain?
8. What known limitations must be preserved?
9. What would a beginner need to debug it?
10. What application-quality risk remains even if the factory run passed?

## Current maturity

At Phase 9.1, the project enforces these dimensions through documentation, a manifest, a validator, tests, and prompt-pack hardening.

This remains deterministic and local-first. It does not yet claim full production observability, live dashboards, real telemetry export, or real LLM-agent evaluation. Those are future scaling phases.
