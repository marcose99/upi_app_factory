2. Problem statement
A payer reports that an account was debited for a UPI transaction, but the beneficiary did not receive the
funds.


Operations teams require a controlled dispute workflow that:


     • preserves transaction and investigation evidence;
     • prevents duplicate case creation and duplicate compensation;
     • distinguishes debit, beneficiary credit, reversal and unknown conditions;
     • records deterministic classifications and reason codes;
     • escalates uncertainty and high-impact cases;
     • enforces human accountability for consequential decisions;
     • provides traceable case history;
     • produces independently verifiable engineering and operational evidence.

The application shall demonstrate a production-shaped architecture without performing real payment
processing, account actions, regulatory filings or live provider interactions.

6.4 Domain invariants

The domain layer shall enforce at least these invariants:


    1. Amount must be greater than zero.
    2. Currency must be an explicitly supported fictional demonstration currency.
    3. Transaction reference must be present and structurally valid.
    4. A case cannot close without a recorded disposition.
    5. A case requiring human review cannot close without an approved human-review decision.
    6. A rejected human-review decision cannot be treated as approval.
    7. An uncertain classification always requires human review.
    8. Contradictory evidence always requires human review.
    9. A high-impact case always requires human review.
   10. Audit history cannot be replaced or reordered through an application service.
   11. An idempotency key cannot be associated with two different payload digests.
   12. A closed case cannot be modified except by an explicitly modelled administrative correction
       workflow.
   13. A classification must include a reason code.
   14. A human decision must include actor, timestamp, rationale and correlation ID.
   15. A disposition shall not represent or execute an actual financial action.

9. Idempotency and concurrency

9.1 Equivalent replay

A repeated request with the same idempotency key and an equivalent canonical payload shall:


      • return the original case identifier;
      • return the original creation result;
      • not create a second case;
      • record an idempotent replay audit event;
      • produce a stable response contract.




                                                         9
9.2 Conflicting replay

Reuse of an idempotency key with a different canonical payload digest shall:


     • fail closed;
     • return an IDEMPOTENCY_CONFLICT error;
     • not alter the original case;
     • not create a second case;
     • record a redacted conflict audit event.

9.3 Concurrent replay

Two concurrent equivalent requests using the same idempotency key shall result in exactly one case.


The generated tests shall exercise concurrent or near-concurrent duplicate submission using deterministic
local execution.


9.4 Optimistic concurrency

Case-changing commands shall carry or enforce an expected case version.


A stale update shall return a structured CONCURRENCY_CONFLICT response and shall not overwrite a
newer case state.

27. Mandatory acceptance scenarios

Scenario A — Successful case creation

Given valid fictional complaint data,
when a case is created,
then a unique case ID is returned,
the case is persisted,
an audit event is recorded,
and the state is RECEIVED or the next valid governed state.


Scenario B — Equivalent idempotent replay

Given an existing request,
when the same idempotency key and equivalent payload are submitted,
then the original case is returned and no duplicate is created.


Scenario C — Conflicting idempotent replay

Given an existing request,
when the same idempotency key is used with a different payload,
then the request fails with IDEMPOTENCY_CONFLICT .


Scenario D — Pending beneficiary credit

Given debit success, credit pending and no reversal,
when the case is investigated,
then classification is PENDING .


Scenario E — Credit failure

Given debit success and beneficiary-credit failure,
when the case is investigated,
then classification is FAILED .


Scenario F — Reversal confirmed

Given debit success and confirmed reversal,
when the case is investigated,
then classification is REVERSED .

Scenario G — Credit confirmed

Given debit success and confirmed beneficiary credit,
when the case is investigated,
then classification is CREDIT_CONFIRMED .


Scenario H — Contradictory evidence

Given contradictory transaction observations,
when classification is attempted,
then classification is UNCERTAIN and human review is required.


Scenario I — High-impact case

Given an amount at or above the configured high-value threshold,
when classification is proposed,
then human review is required.


Scenario J — Missing evidence

Given incomplete required observations,
when resolution is attempted,
then the case cannot close and more evidence or human review is required.


Scenario K — Invalid transition

Given a case in RECEIVED ,
when direct closure is attempted,
then the operation fails with INVALID_STATE_TRANSITION .


Scenario L — Unauthorised actor

Given a customer-support actor,
when a supervisor-only decision is attempted,
then the operation fails with UNAUTHORISED_ROLE .


Scenario M — Restart persistence

Given a persisted case,
when the local application restarts,
then the case, idempotency record, audit events and review decisions remain available.


Scenario N — Audit tampering

Given an altered audit record,
when audit integrity is verified,
then verification fails and the case is quarantined or blocked from closure.
