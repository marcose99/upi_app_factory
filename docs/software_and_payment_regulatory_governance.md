# Software-Engineering and Payment Regulatory Governance Alignment

## Purpose

This document defines how `upi_app_factory` should align with software-engineering industry standards and payment-domain regulations while preserving honesty labels and mock boundaries.

This is **regulatory alignment, not certification**.

The project must not claim legal compliance, regulatory approval, scheme certification, NPCI certification, RBI approval, PCI DSS certification, ISO certification, or production readiness unless the required official evidence, independent review, and certification process are completed.

## Governance principle

The factory must be governed at two levels:

1. **Factory governance**: how the agentic software factory plans, generates, validates, evaluates, observes, audits, and releases work.
2. **Generated-application governance**: how applications generated by the factory meet software life cycle quality, security, observability, auditability, and payment-domain expectations.

## Software engineering regulatory alignment

The factory should align with the following software-engineering and secure-delivery bodies of practice:

- NIST SSDF for secure software development practices.
- OWASP guidance for web, API, and LLM/GenAI application risks.
- SLSA-style provenance for generated artifact origin, build context, and reproducibility evidence.
- OpenTelemetry-compatible thinking for logs, metrics, traces, correlation IDs, run IDs, agent IDs, and workflow step IDs.
- Secure SDLC practices covering requirements, architecture, design, coding, testing, security review, release readiness, operations, and incident response.

## Payment regulatory alignment

For Indian digital-payment and UPI-style systems, the factory must treat the following as regulated-domain references requiring official-source grounding:

- RBI directions and notifications for digital payment security controls.
- RBI directions for online dispute resolution for digital payments.
- RBI customer-protection and unauthorized electronic banking transaction liability guidance.
- NPCI UPI circulars, operating guidance, and product references.
- PCI DSS where cardholder data, card rails, or card-payment scope is introduced.
- DPDP Act / digital personal data protection obligations where personal data is processed.

## Mocked ecosystem boundary

The generated application may be designed with near-certifiable quality posture, but the surrounding ecosystem must remain mocked unless explicitly approved and evidenced.

Allowed in current project:

- mock UPI switch
- mock core banking
- mock customer notification
- mock dispute evidence store
- synthetic transaction data
- synthetic dispute workflows

Not allowed without separate approval and evidence:

- real bank integration
- real PSP integration
- real NPCI integration
- real UPI certification claim
- real customer data
- real payment settlement
- real regulatory compliance claim

## Generated application expectation

Generated applications should be:

- highly modular
- industry standard
- aligned with the complete software life cycle
- near-certifiable in quality posture without claiming actual certification
- built with explicit contracts, ports, adapters, services, validators, tests, observability hooks, support notes, and mock-boundary declarations
- beginner-readable and debug-friendly
- safe to review, regenerate, validate, and explain

## Regulatory evidence model

Every future regulation-sensitive artifact should link to:

- regulation/source ID
- source name
- source URL
- source owner
- source type
- applicability status
- requirement/task/policy/evidence references
- mock-boundary status
- known limitations

## Practical acceptance rule

A generated artifact is incomplete if it says it is high quality but does not answer:

1. Which software-engineering standards influenced it?
2. Which payment regulations or official payment-domain references may apply?
3. Which sources are official and which are missing?
4. Which ecosystem components are mocked?
5. Which claims are explicitly not being made?
6. What must be validated before production use?
7. What must be reviewed by compliance, security, legal, and domain experts?

## Current maturity

At Phase 9.3, this project adds a regulatory governance source registry, regulatory applicability matrix, validator, tests, and prompt-pack hardening.

This remains a learning and demonstration baseline. It is not a production payment system and is not certified.

## Validator-required exact regulatory terms

This section intentionally preserves exact governance terms used by deterministic validators.

- payment regulatory alignment must be explicit for payment-domain work.
- MISSING_OFFICIAL_SOURCE must be used when an official source is not yet available or not yet reviewed.
- MOCK_BOUNDARY must be used when the ecosystem, integration, upstream system, downstream system, payment network, bank system, or regulatory interface is mocked.
- SYNTHETIC_DATA must be used when examples, transaction records, dispute records, customer records, or evidence are synthetic.
- Regulatory alignment, not certification remains the controlling claim boundary.
- Software-engineering governance and payment regulatory governance must both be considered before generated applications are accepted.
