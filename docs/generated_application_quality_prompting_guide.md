# Generated Application Quality Prompting Guide

## Purpose

This guide defines the prompt expectations for applications generated by the
factory. It complements the existing two-layer quality model by making the
**generated application** standard more explicit.

The factory must not only run well. The application produced by the factory
must also be highly modular, industry standard, lifecycle-aligned, and near
certifiable in its engineering posture while keeping every surrounding external
ecosystem dependency mocked unless explicitly approved.

## Mandatory generated-application standard

Every generated application must be designed and reviewed as if it could later
move toward production certification, while honestly preserving current limits.

The generated application must be:

- **Highly modular**: separate domain logic, API routes, contracts, services,
  adapters, validation, tests, and operational concerns.
- **Industry standard**: use clear layering, typed contracts, validation,
  deterministic tests, safe errors, security checks, and release evidence.
- **Near-certifiable in quality posture**: include traceability, validation,
  evaluation, observability, security, testability, operational readiness,
  and review evidence, without claiming actual certification.
- **Beginner-readable and debug-friendly**: prefer clear names, small modules,
  direct control flow, helpful errors, and practical debug notes.
- **Mock-safe**: all out-of-scope ecosystem dependencies must be represented
  through explicit mock boundaries, not hidden production integrations.

## Recommended modular application architecture

Use a lightweight but production-disciplined style:

1. **API layer**: routes, request/response schemas, error contracts.
2. **Contract layer**: Pydantic models, typed inputs, typed outputs, state
   transition contracts, and public service interfaces.
3. **Domain layer**: business concepts, domain decisions, invariant checks,
   and workflow state transitions.
4. **Application service layer**: orchestration of use cases without leaking
   transport or infrastructure concerns.
5. **Ports and adapters layer**: explicit interfaces for external systems and
   mock adapters for the surrounding ecosystem.
6. **Validation layer**: input validation, business validation, state validation,
   mock-boundary validation, and policy validation.
7. **Testing layer**: unit, API, contract, negative, boundary, regression,
   security-oriented, and smoke tests.
8. **Observability layer**: health/readiness, structured logs later, correlation
   IDs later, metrics later, traces later, and actionable failure signals.
9. **Operations layer**: startup, validation commands, troubleshooting notes,
   known limitations, and supportability guidance.
10. **Evidence layer**: requirement IDs, task IDs, policy IDs, evidence refs,
    hashes where applicable, validation reports, and release-readiness notes.

## Mocked ecosystem requirement

Every generated application must keep the surrounding ecosystem mocked until a
separate integration approval exists.

For this project, examples include:

- mock UPI switch
- mock core banking
- mock customer notification
- mock dispute evidence store
- mock upstream data source
- mock downstream integration

A generated application must not hide calls to real payment systems, banking
systems, PSPs, regulators, notification providers, or production data stores.
If official sources or real integration details are missing, the application
must preserve `MISSING_OFFICIAL_SOURCE`, `MOCK_BOUNDARY`, and `SYNTHETIC_DATA`.

## Prompting checklist for generated applications

Every future prompt that asks an agent to generate or review application code
must include these expectations:

- generated application quality dimensions
- highly modular design
- industry standard software life cycle coverage
- near-certifiable quality posture without false certification claims
- mocked ecosystem boundaries
- explicit ports and adapters
- explicit API and data contracts
- validation and evaluation
- observability and operational readiness
- security and testability
- traceability and auditability
- beginner-readable and debug-friendly implementation

## Acceptance rule

A generated application is not acceptable merely because code exists or tests
pass. It must also be explainable, traceable, validated, evaluated, observable,
secure, modular, supportable, mock-safe, and honest about limitations.

## Exact validator phrase coverage

This guide intentionally includes the exact phrase **Generated-application quality dimensions** because every governed agent prompt must use this phrase when evaluating generated applications.

For generated applications, the factory must explicitly cover compliance, traceability, auditability, validation, evaluation, observability, security, testability, operational readiness, contracts, ports and adapters, mocked ecosystem boundaries, near-certifiable quality posture, industry standard software life cycle coverage, highly modular design, beginner-readable implementation, debug-friendly implementation, MOCK_BOUNDARY, MISSING_OFFICIAL_SOURCE, and SYNTHETIC_DATA.

Compliance means preserving approved policies, honesty labels, mock boundaries, official-source limits, evidence expectations, and review readiness without making false certification or regulatory claims.
